# N0b — separate frozen synthetic labeled version, 2026-10-27

Freeze precedes all target generation. N0 data/splits and N1/RULE.md are immutable inputs. Stop after labels/report: no probes, residual extraction, teacher-forcing experiments, or steering in this step.

## Scenarios and split

60 newly authored scenario families × 4 package characters = 240 scenarios. R1 18 families/72 scenarios; R2 18/72; R3 12/48; R4 12/48. Fixed seed 20261027, within-category family shuffle: R1/R2 11 dev + 7 heldout families each; R3/R4 7 dev + 5 heldout each. Total 36/24 families, 144/96 scenarios (60/40). Explicit assignment is scenarios/split.json. All characters, arms and decodes of a family stay on its one side. No reassignment or positive-dependent supplementation. A shortfall is reported; it does not justify editing this version.

R1 covers user-only, character-only, parallel relations, identical/similar names and antecedent distances 1–6 user-turn transitions. Distance counts the final question as the next turn, with 0–5 intervening user/model exchanges. Family names designate complete antecedent/event/question archetypes; they do not assert generalization to an unseen broad category such as all pets or all tasks. Some broad motifs recur across splits. Scripted history is authored, not generated; no generated response enters another scenario. Unspecified package relations stay unspecified. Only supplied package relations may be used; private names and canon details are redacted.

Package canon: four fixed private bench packages A–D; package contents are not distributed.

Prompts use stable_layout and gemma_prompt from the life_facts_who pre_edit renderer, its historical app template fixture, and existing diagnose_notes first-conversation/identity/who note functions. Their source hashes are recorded. The who ledger follows package priority, including omission of a colliding user name from that note; original user turns still carry the distinction. Both notes are per-turn notes, not new instructions invented for this dataset. This is a controlled replay of these research snapshots, not a claim that the live app has been run. Other common first-sitting/date/wake notes remain constant across arms. Do not apply app reply-prefix injection or retries.

## Generation

Arms: a = character LoRA + who/identity notes when applicable; b = same LoRA without those two notes; c = base without adapter + same notes as a. Each of the 720 arm-prompts gets greedy and two temperature 0.8 samples (seeds 20261027, 20261028): planned 2160 replies. Greedy is argmax. Stochastic decoding is full-vocabulary softmax(logits/0.8), no top-k/top-p/min-p/repetition penalty. Each reply initializes its own CPU torch Generator with its seed; sample on CPU from the GPU-computed distribution. Sampling computation is on the compute machine, never Mac model inference. Max 96 generated tokens including EOG; stop on ids 1 or 106. Preserve cap/truncation and raw bytes.

Use existing laptop N0 LoRA ExactEngine and numerical caches, no weight edits, no pushes. Sequential one-row forward with cached common 64-token prefill chunks, preserving the numerical microbatch schedule and exact tokens. Immutable KV prefix caches may be reused; never reuse a cache across adapters. Record prompt token IDs, generated token IDs, rendered prompt hash, engine/model/adapter hashes, seed/temperature and timings for every reply. Vocabulary-only tokenization is allowed and does not perform Mac inference; record it explicitly. Reuse existing libraries without downloads.

Checkpoint every completed reply and every arm; resume by stable IDs with hash validation. About three GPU hours; pause while external GPU memory exceeds 3072 MiB, with checks before prefill chunks and periodically in decode. Never kill unrelated processes. Budget is measured generation wall time excluding recorded external-memory pauses; if the approximate three-hour budget cannot fit, preserve the partial result and state the shortfall, without shortening prompts or changing decoding. Network only ssh/scp; no git, deletion, voice paths, downloads or real chats.

## Independent blinded GPT labels

Two different available Codex GPT models: gpt-6.1-sol and gpt-6.1-terra. If one is unavailable, use separately initialized sessions of the available model with different packet orders, recording actual model/session metadata. Judge sessions have no shared history and never read the other judge's files. Parallel disjoint shards are permissible, each reply has one decision from each model. No regex/model-generated proxy labels may substitute for GPT reading.

Packets expose opaque reply IDs, complete rendered prompt, character package canon and reply, plus current user context. Hide adapter, arm, temperature, split, intended category, family IDs and reference interpretations. System note differences are visible because full context is required, but arm names and provenance are withheld. Each judge independently reads all four categories on every reply, even when the scenario was targeted elsewhere. Exact duplicate (character, rendered context, reply) can share one judgment per judge; maintain an explicit mapping back to each reply. Different contexts never share labels just because the answer text matches.

R1: yes only for an owner attribution error, user ↔ character or other person; ordinary unsupported self-life detail is not automatically ownership confusion. Record every mentioned relation/person/pet as text, true_owner and surface_owner (user/character/third_party/shared/unknown), and evidence spans. Resolve pronouns in context; indirect reported speech is not literal speaker ownership. Ambiguous surface owner is unknown, not a forced positive.

R2: yes for a person-character assuming assistant identity: assistant_offer, AI_self_reference, capability_list, disclaimer (multiple kinds allowed). A direct task answer or ordinary peer help alone does not establish assistant identity. Assess package humanInWorld and admitsAI, and distinguish a natural in-character admission of uncertainty from a professional/AI disclaimer. Record the decisive span.

R3: none/mild/strong under ai_review_v2's original (다) rubric and T01–T30 catalog. Read not_instances first. None = no confirmed tone item. Mild = 1–2 weak items plus user-specific concrete content. Strong = any strong item, T01, ≥2/3 formula sentences, or nothing substantive after removing formulas. A brief justified sympathetic reply is not automatically formulaic. Do not turn grammar/fact errors into tone errors; follow original attribution precedence. No app fixed prefix is present. Record IDs and spans.

R4: yes for a definite unsupported or contradicted claim about previous conversation/shared experience, memory, dates/time, or recorded routine/wake state. Do not fill a false premise. Uncertainty/question/explicit hypothetical is not a positive. Canon-consistent incidental own-life narration alone is not confabulated memory; a specific past-event claim presented as remembered or recorded needs evidence. Record decisive claim/evidence spans. User requests do not prove an event occurred.

Primary AI agreement is exact equality of R1 yes/no, R2 yes/no, R3 three-way severity, R4 yes/no; R3 positive = mild or strong only after severity agreement. Compute ordinary unweighted Cohen κ for each primary label over all double-judged replies; also publish binary R3 κ. If expected agreement=1, κ is undefined, not 1 by convention. Report unique-context unit κ as sensitivity because arms/samples can duplicate. Keep every primary disagreement in a separate file, without adjudication. Preserve both independent annotation sets; disagreement on owners/kinds/catalog/spans is separately flagged and not called annotation agreement. For downstream owner analysis require both judges' owner attribution to match; span alternatives remain explicit.
